   mapping_array(array, func) 必须对每个元素调用 func，并返回结果数组。
   证据 A：tools/importd_disasm.txt 的 importd::create_data
       [ 9] new_func(141, capture=0)
       [12] call_efun(explode, nargs=2)        ; explode(str, "\n") 得到每行
       [13] call_efun(mapping_array, nargs=2)  ; 把每行字符串过一遍 func#141
   证据 B：gs/daemons/scand.c::query_objects 结尾
       items = mapping_array(obs_arr, (: find_basic_object_by_import_name :));
       调用方要求元素是"对象"（instruction_1::query_task_weapon 里 is_object(basic)）。
   现状错误：builtins.cpp 里是"忽略 func、原样返回入参数组"的近似实现 -> scand 那条链返回
   import_name 字符串 -> 新手上任务 S11"张老板发武器"走进
       me->prompt_by(npc, "奇怪，怎么找不到了呢？我再找找，你过会儿再来。");

        商店 = dealer.list，两条都不经过 mapping_array，所以只有武器这一步坏。

2) 两次尝试与失败记录（都已 revert）
   a. builtins + applyClosureOnOwner（经调度器 execOnMain 嵌套执行）：启动卡死 >20 分钟，
      gs 内存停在 313MB 不动。
   b. VM 内 callEfunWithArgs 内联执行（executeFunctionFromOutside）：启动栈溢出
      [crash] code=0xc00000fd；主线程栈 32MB -> 256MB 仍然溢出。崩溃时 LPC 环：
      get_config safe_load_object safe_load_object create register_post_init safe_load_object …
   → 即：mapping_array 一旦真的执行闭包，启动期的装载链（路径 -> safe_load_object -> create ->
     register_post_init -> …）就会深到撑爆栈；我们目前是"靠 mapping_array 不干活"绕开了这条链，
     而原版靠的是装载器自身的 in-progress 语义 + 每层调用极小的 C 栈。
