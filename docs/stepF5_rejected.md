## 已定位到的机制（供以后重做时用）

失败克隆体的日志（vF9，`login.o#17408`）显示：

```
[case8] process_command args=[create_new_char | ({"rf5c",1,1,1})]
[ev] wait ev_filed0 mask=0x400            <- do_operate 挂起等 dba 回包
[ev] wait-probe ev_filed0 mask=0x400 -> -501
（随后 20 次 create_new_char 全部 op=1 -> 全部回 9101）
```

即：建角的链挂在 `ev_filed0` 上等 dba 回包；回包走 **cno=2 那条内部连接**。
旧实现里**每个连接一个读取线程**，回包由它自己的线程立刻喂进去、立刻 raise
事件、立刻唤醒挂起的链；邮箱版本让回包必须等调度器迭代来 drain，而这时
调度器正在跑别的活（客户端连发、daemon 轮转）。窗口一错开，链就等不到事件，
名字却已经被 `check_valid_name/get_gid` 占掉 —— 于是客户端看到「名字已存在」，
列表永远是空的。

**这解释了为什么三次都失败、而基线稳定：问题不在"谁来读"，在"回包什么时候
被交给 VM"。** 原版没有这个问题，是因为它每轮 `poll` 所有 fd、**每个 fd 一次
回调**，回包的投递延迟被压在同一个事件循环里；我们只要还保留"调度器迭代"
这一层，就必须保证回包不被客户端突发挤到后面（vF12 的优先级规则方向对，
但一 tick 的结算规则又把客户端自己的包压住了，仍然不够）。

## 如果之后还要做 F5，建议的顺序

1. 先把 `waitFlowSettled`/`waitClientCommandIdle` 的语义在单线程模型下精确
   复刻（回包 → 事件 → 唤醒链 → 链跑完 → 才读下一包），写成一个可观测的
   状态机（`[flow] cno=.. stage=..`）；
2. 把 dba/ccs 内部连接做成**独立于客户端队列的高优先通道**，并保证它们的
   投递不受预算限制；
3. 只有当 1+2 在"建角 20 连击"下稳定 3/3，再谈把读取线程去掉。

**在此之前，F4（accept 收进调度器扫描）是这条线上唯一通过真值验收的改动，
应当保留。**
